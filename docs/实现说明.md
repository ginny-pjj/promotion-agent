## 一、设计思路

### 1.1 输入与输出

输入有三类：

| 输入 | 说明 |
|---|---|
| 抖加申请总结 | 群里的抖加汇总文本：博主、金额、支付人 |
| 付款（垫付）申请总结 | 垫付汇总文本：达人、金额、打款人、预计打款日期 |
| 推广账号表 | 公司现有 Excel 主表，作为匹配与写入的基准 |

输出有两类：

| 输出 | 说明 |
|---|---|
| 负责人汇报 | 汇总金额、明细条数、异常清单、处理结论 |
| 推广账号表测试副本 | 在原表结构上填入当天数据，原表不动 |

### 1.2 分层与边界

抽取 → 规则校验 → 人工确认 → 输出，四层单向依赖。

贯穿全程的一条硬规则：**判断归代码，措辞归人。**

- 金额加总、笔数核对、日期判断、重复与缺失检测，全部由确定性代码完成
- 大模型只用于非固定格式文本的抽取和汇报文案润色，不参与金额计算，也不参与「是否放行」的裁决
- 当前演示数据的格式固定，抽取层用正则即可覆盖，因此运行时**不依赖大模型 API**，离线也能完整演示

### 1.3 数据保护

程序只读原始测试表、只写副本。`excel_writer.update_workbook()` 在输入与输出路径相同时直接抛错，避免误覆盖正式数据。

## 二、数据异常的处理原则

题目材料本身就带有矛盾与缺失，例如：

- 垫付文本声称 7 笔，明细只列出 5 条
- 垫付文本的「预计打款日期」早于申请日期
- 推广账号表中 `葵花夫妇` 出现两行，其中一行抖音号为空
- `张栋梁` 在表中有抖加记录，但两份申请文本里都没有它的来源
- `发布日期` 列出现 `4.1`、`4.9` 这类非日期值
- `马马马叔` 标记「已打款」，但打款人与打款日期都是空的

统一处理原则：**标记 + 转人工，不猜测、不自行放行。**

代码只负责发现「这两处对不上」，不负责判定哪一处才是事实——真相由负责人裁定。这是需求里「不要自行猜测」的直接落地。

## 三、开发过程中发现并修正的问题

### 问题 1：把「预计打款」写成了「已经打款」

垫付文本给的是「预计打款日期」，最初实现直接把它写进了 Excel 的「打款日期」列。业务上这是两回事：把计划当成已完成，负责人会误以为款项已经付出。

改法：不再写入「打款日期」列，改为写进备注（例如 `待人工确认；预计打款：2026-08-31`），待负责人核实后再进入正式流程。

### 问题 2：Excel 中日期显示成 46265

写入 `date` 对象后，单元格没有日期格式，打开看到的是 Excel 的日期序列值。业务同事不懂这个，会以为程序算错了。

改法：写入日期的同时设置 `number_format = "yyyy-mm-dd"`，让人一眼能看懂。

### 问题 3：账号名差一个字，自动匹配还是转人工

文本里写「唐山第一女渠工」，表格里是「唐山第一女泵工」。模糊匹配实现起来不难，但很容易写错行、填错金额。

选择：匹配不上就报异常转人工，由负责人决定对应哪一行，而不是让程序自己猜。涉及钱的场景宁可多一步人工，不能静默失败。

## 四、验证方式

- **单元测试**：`python -m pytest`，覆盖文本抽取、金额/笔数/日期校验、人工确认触发、账号不匹配
- **端到端**：用示例文本 A / C 跑完整流程，检查生成的 Excel 副本与汇报在业务上是否讲得通
- **对抗输入**：构造总额不符、笔数不符、日期倒挂、账号名差一字的输入，确认系统报异常而不是静默通过

## 五、开发方式

项目骨架、网页界面与文档初稿由 AI 编程助手（Cursor）生成；设计边界与验收标准由我确定，第四节的三类验证我逐条跑过，上面三个问题都是在验证过程中发现并修正的。

## 六、后续规划

- 文本格式变得不固定时，在抽取层接入大模型，其余各层不变
- 汇报与人工确认单通过企业微信自建应用推送给负责人，替代当前的手动转发
- 补齐表格侧校验：表内重复行、表中有但文本无来源、打款字段半填、非日期值
- 冲突时不覆盖：表中已有值与文本不一致时标记待确认，而不是直接改写
